# 天気表示の選定・設計

## 目的と範囲

東京都の1地点について、今日を含む今後5日間の予報をホームに表示する。予報の取得APIと天気カードは実装済み。shadcn-svelteのCardとLucideの静止アイコンを利用する。

- 日別5日分：天気・最高／最低気温（℃）・平均相対湿度（%）。
- 日付の区切りは`Asia/Tokyo`にそろえる。
- 屋外の予報値であり、室内の温湿度や自宅での実測値ではない。

## 対象地点の指定

Open-Meteoの予報APIには、地名ではなく緯度・経度を指定する必要がある。表示名と取得地点の緯度・経度を組にして設定する。

| 表示名 | 取得地点           | 緯度（北緯） | 経度（東経） |
|--------|--------------------|--------------|--------------|
| 東京都 | 東京都庁（新宿区） | 35.689444    | 139.691667   |

行政庁舎は場所と出典を確認しやすいため、初期の固定地点として採用する。気象観測所を指定するものではなく、予報APIへ渡す位置の基準とする。

- 東京都：[東京都総務局統計部「よくある質問」の「東京の位置を知りたい」](https://www.toukei.metro.tokyo.lg.jp/faq/fq-faq.htm)が、都庁所在地を北緯35度41分22秒・東経139度41分30秒と案内している。この値を「度＋分÷60＋秒÷3600」で十進数へ変換し、小数点以下6桁に丸めた。

「東京都」は都全域の平均ではなく、東京都庁を代表地点とした予報を意味する。最初は地点を固定し、地名検索や地点の追加・編集画面は作らない。

## Open-Meteoの選定理由

通常のWeather Forecast APIを採用し、まずは既定のモデル選択を利用する。

| 要件           | 判断                                                       |
|----------------|------------------------------------------------------------|
| 無料           | 個人の非商用用途で無料枠を利用でき、APIキー・登録が不要    |
| 日本の地点指定 | 緯度・経度を指定できる                                     |
| 5日間の予報    | 必要な5日分の取得に対応する                                |
| 湿度           | 日平均の相対湿度を取得できる                               |
| 精度の検討     | 利用する気象モデルが公開され、モデルを指定して比較もできる |

「日本で最も正確」と確認できたための選定ではない。今回の無料・地点指定・期間・湿度の要件を満たし、導入と運用を小さく始められるため選ぶ。対象地域の精度が問題になったら、気温の誤差や雨の有無を予報期間別に検証し、モデルや提供元を見直す。

地点を細かく指定できても、その細かさで予報されるとは限らない。また、Open-MeteoのJMAモデル利用は気象庁が発表する週間予報そのものではない。JMA APIで提供される約5kmのMSMは4日先までで、予報期間全体を通して同じ解像度ではない。

比較したMET Norwayは無料で9日先まで取得できるが、日本では全球モデルを使用する。Visual Crossingも無料枠で週間予報と湿度を取得できるが、通常APIとは無料枠・認証の扱いが異なる。OpenWeatherの通常無料枠は5日で今回の期間を満たす。WeatherAPI.comの無料枠は3日で、今回の5日間を満たさない。

無料APIの利用上限と出典表示の条件を守り、画面にOpen-Meteoへのクレジットを付ける。商用化する場合は無料枠の適用条件を再確認する。

## 取得方式：Go側のメモリキャッシュ

```text
画面 → Goの天気API
         ├─ 有効なキャッシュあり → 保存済みの取得結果を返す
         └─ 未取得・期限切れ     → Open-Meteoへ取得し、成功結果をキャッシュして返す
```

初期値は30分を有効期限とする。これは気象モデルの更新周期を意味せず、画面の鮮度と外部通信回数のバランスを取るための設定値。必要に応じて調整する。

- ブラウザから外部APIを直接呼ばず、Go側で取得・変換する。
- 再読み込みや複数ブラウザからのアクセスでも、同じ地点の取得結果を共有する。
- アクセスがない間は取得しない。定期実行や取得用コマンドは作らない。
- 同時アクセス時の重複取得を抑え、失敗した取得結果で正常なキャッシュを上書きしない。
- 日付が変わった場合は期限内でも再取得し、今日の表示と予報日を一致させる。
- 有効なキャッシュがなく取得に失敗した場合はエラーを返す。古いデータの代替表示は初期実装では行わない。
- API再起動時はキャッシュを失い、次のアクセスで再取得する。

1日1回だけの取得は、日中の予報変更を反映しにくいため採用しない。期限付きキャッシュなら、毎回外部APIへ接続する方式より通信を抑えつつ更新できる。

### キャッシュの実装

`apps/api/usecase/weather`の`NewForecastCache(reader, now)`で生成し、`Get(ctx)`で取得する。`now`は時刻を取得する関数で、本番では`time.Now`、テストでは固定時刻を返す関数を渡す。依存先の`ForecastReader.ReadForecast(ctx)`は取得・変換・検証済みの`domain/model.WeatherForecast`を返す契約とする。`main`でOpen-Meteoクライアント・Reader・キャッシュ・Handlerを1回生成し、各リクエストで共有する。

- 取得日時`FetchedAt`から30分未満、かつ日本時間で同じ日付なら再利用し、`FetchedAt`を更新しない。30分ちょうどから期限切れとする。
- `sync.Mutex`で確認・取得・保存をまとめて保護し、正常な取得が完了した後のリクエストは同じ結果を使う。
- 取得失敗はエラーを返して保持済みのキャッシュを残す。期限切れの値は返さず、次のリクエストで再取得を試みる。
- 返却するスライスと気温・湿度のポインターはコピーし、呼び出し側で値を変更してもキャッシュに影響しないようにする。
- テストでは時刻を固定し、有効期限の境界、日本時間の日付変更、取得失敗と再試行、同時アクセス、返却値からの書き換え防止を確認する。

## 今回DBへ保存しない理由

目的は最新の取得結果を表示することで、過去の天気や予報の変化を保存・分析する要件がないため。キャッシュは失っても再取得できるデータとして扱う。

| 保存先     | 利点                                                   | 今回の判断                                                         |
|------------|--------------------------------------------------------|--------------------------------------------------------------------|
| Goのメモリ | テーブルや保存処理を追加せず、期限付きの再利用ができる | 単一APIプロセスでの個人利用には十分                                |
| MySQL      | 再起動後も保持でき、履歴や複数プロセス間で共有できる   | 現時点では永続化が必要な用途がなく、保存・更新・削除の管理が増える |

DBが不適切という判断ではなく、現在の要件では必要ないという判断。予報と実測の比較、電気代などとの分析、再起動後も残す履歴、取得時点ごとの予報保存が必要になったらDB保存を検討する。予報の履歴と実測の履歴は別のデータとして設計する。

## 画面に示す日時

日別予報の対象日と、Go側の最終取得日時を区別する。キャッシュを返す際も取得日時は更新せず、最後に外部APIから取得した時刻を表示する。

## 天気APIのインターフェース

`GET /v1/weather/forecast`で、東京都の今日を含む5日間の予報を返す。リクエストボディ・クエリパラメーターは不要。地点・期間・タイムゾーンはGo側で固定する。Caddy・Vite経由では`GET /api/v1/weather/forecast`を呼び出す。

成功時は`200 OK`、`Content-Type: application/json`を返す。以下の値は形式を示す架空の例。

```json
{
  "location_name": "東京都",
  "fetched_at": "2026-10-31T09:00:00+09:00",
  "forecasts": [
    { "date": "2026-10-31", "weather": "clear", "temperature_max": 21.5, "temperature_min": 13.2, "relative_humidity_mean": 62 },
    { "date": "2026-11-01", "weather": "overcast", "temperature_max": 20.1, "temperature_min": 14.0, "relative_humidity_mean": 68 },
    { "date": "2026-11-02", "weather": "rain", "temperature_max": 18.3, "temperature_min": 13.5, "relative_humidity_mean": 81 },
    { "date": "2026-11-03", "weather": "overcast", "temperature_max": 19.4, "temperature_min": 12.8, "relative_humidity_mean": 70 },
    { "date": "2026-11-04", "weather": "clear", "temperature_max": 20.6, "temperature_min": 12.1, "relative_humidity_mean": 59 }
  ]
}
```

| フィールド                           | 型                 | 意味                                                                                |
|--------------------------------------|--------------------|-------------------------------------------------------------------------------------|
| `location_name`                      | string             | 表示名。初期値は`東京都`                                                            |
| `fetched_at`                         | string             | Go側が外部APIから取得に成功した日時。RFC 3339形式。キャッシュ利用時も元の日時を返す |
| `forecasts`                          | array              | 今日から日付の昇順で5件。日付の基準は`Asia/Tokyo`                                   |
| `forecasts[].date`                   | string             | 予報の対象日。`YYYY-MM-DD`形式                                                      |
| `forecasts[].weather`                | string             | 天気を表すenum。下表に従ってGo側で変換し、未対応・欠損なら`unknown`                 |
| `forecasts[].temperature_max`        | number または null | 日最高気温（℃）                                                                     |
| `forecasts[].temperature_min`        | number または null | 日最低気温（℃）                                                                     |
| `forecasts[].relative_humidity_mean` | number または null | 日平均の相対湿度（%）。現在の湿度とは異なる                                         |

上記のキーは省略しない。気温・湿度はJSONの数値で返し、外部APIで欠損している項目だけ`null`にする。画面では`null`を`—`と表示し、0として扱わない。フロントは`weather`のenumを日本語表示名・アイコンに対応させる。

### 日付・タイムゾーンの扱い

自作APIのレスポンスに`timezone`は含めない。対象は東京に固定し、`date`は日本時間での暦日としてそのまま表示する。日付だけの値をUTCの日時として解釈して変換しない。`fetched_at`は`+09:00`などのオフセットを含むため、取得日時の表示に別の`timezone`フィールドは不要。

一方、GoからOpen-Meteoへの取得には`timezone=Asia/Tokyo`を指定する。[公式仕様](https://open-meteo.com/en/docs)では日別データの取得にタイムゾーン指定が必要であり、表示時の変換だけでなく、最高／最低気温・平均湿度を集計する1日の境界を日本時間にそろえるために使う。

### 天気のenumと外部コードの対応

[Open-Meteo公式の天気コード一覧](https://open-meteo.com/en/docs#weathervariables)には29個のコードがある（2026-10-31確認）。自作APIでは強度など一部の違いをまとめ、以下の16種類（`unknown`を含む）の文字列enumに変換する。OpenAPIにもこのenumを定義し、Go・TypeScriptの型を生成する。

| `weather`のenum          | 日本語表示例     | Open-Meteoのコード   |
|--------------------------|------------------|----------------------|
| `clear`                  | 快晴             | 0                    |
| `mainly_clear`           | 晴れ             | 1                    |
| `partly_cloudy`          | 晴れ（一部に雲） | 2                    |
| `overcast`               | 曇り             | 3                    |
| `fog`                    | 霧               | 45, 48               |
| `drizzle`                | 霧雨             | 51, 53, 55           |
| `freezing_drizzle`       | 着氷性の霧雨     | 56, 57               |
| `rain`                   | 雨               | 61, 63, 65           |
| `freezing_rain`          | 着氷性の雨       | 66, 67               |
| `snow`                   | 雪               | 71, 73, 75           |
| `snow_grains`            | 霧雪             | 77                   |
| `rain_showers`           | にわか雨         | 80, 81, 82           |
| `snow_showers`           | にわか雪         | 85, 86               |
| `thunderstorm`           | 雷雨             | 95, 97               |
| `thunderstorm_with_hail` | ひょうを伴う雷雨 | 96, 99               |
| `unknown`                | 不明             | 未対応のコード・欠損 |

日本語表示は本アプリでの対応案であり、気象庁の天気予報の表現を再現するものではない。日別の`weather_code`は、その日の最も厳しい天気を表す。「晴れのち雨」などの時間的な変化は表現しない。コード96・99はひょうを明示的に予測するモデルに限られるため、すべてのモデル・地域で返されるとは限らない。

台風専用のコードはない。台風の影響下でも、このAPIは雨・雷雨などの天気を返すもので、台風の有無や接近を判定できない。今回は台風情報を表示対象に含めず、必要になったら別の情報源から取得する。

### エラー時の扱い

| ステータス | 条件                                                                                         |
|------------|----------------------------------------------------------------------------------------------|
| `200`      | 外部APIまたは有効なキャッシュから5日分を返せる                                               |
| `502`      | 外部APIへの通信失敗・タイムアウト・不正なレスポンス。必要な5日分の日付がそろわない場合も含む |
| `500`      | Go側の予期しない内部エラー                                                                   |

エラーのJSON形式は既存APIと同じ`{"message":"天気予報を取得できませんでした"}`とする。外部APIのレスポンスや内部エラーの詳細はそのまま公開しない。期限切れのキャッシュや空配列を成功レスポンスの代わりに返さない。

取得・検証で失敗した元のエラーは、Handlerで`get weather forecast:`を付けて標準ログへ出力する。`docker compose logs --tail 100 api`で、タイムアウト・DNS・TLS・外部HTTPステータス・データ検証のどこで失敗したかを確認する。Caddy経由で502になった場合は、ラズパイ上の`http://127.0.0.1:8080/v1/weather/forecast`へ直接アクセスし、API自身の502かCaddyの転送失敗かを切り分ける。

この契約は`openapi/paths/weather-forecast.yaml`と`openapi/schemas/weather-forecast.yaml`に定義し、Go・TypeScriptのレスポンスモデルを生成する。取得・変換・検証・キャッシュをHandlerとルートに接続し、ホームの天気カードから呼び出す。

## フロントの表示

- `src/api/weather-forecast.ts`で`/api/v1/weather/forecast`を呼び出し、生成済みの`WeatherForecastResponse`を利用する。
- `src/models/weather-forecast.ts`で16種類の天気enumと日本語表示名を対応付ける。
- `src/components/WeatherForecastCard.svelte`は取得結果と読み込み・エラー状態を受け取り、5日分を表示する。カードの最大幅を448pxとし、5日分を横並びでコンパクトに表示する。
- `App.svelte`のマウント時に1回取得する。取得結果は画面の表示用に保持し、共有ストアやブラウザ側キャッシュは追加しない。
- 天気と騰落率を独立して取得し、片方の失敗で他方の表示を妨げない。
- 天気の対象日は`10/31（土）`のように曜日付きで表示する。`src/models/weather-forecast.ts`でAPIの暦日からUTCの日時を作り、曜日の整形もUTCに固定して端末のタイムゾーンによる日付のずれを防ぐ。取得日時は日本時間に整形する。気温・湿度のnullは「—」、0は数値として表示する。
- 読み込み中・取得失敗・データなしを区別し、Open-Meteoへの出典リンクを表示する。
- `src/components/WeatherIcon.svelte`で16種類のenumをLucideアイコンへ対応付ける。絵柄を共有する区分でも日本語名は残し、装飾アイコンには`aria-hidden="true"`を付ける。アイコンはビルドに含め、表示時の外部取得や昼夜による切り替えは行わない。
- shadcn-svelteのCardを使用し、ダークな背景・グリーンのアクセント・共通の角丸と余白で株価カードと統一する。狭い画面でも5列を保ち、気温の数値だけ必要に応じて折り返す。長い天気名は省略表示し、title属性と読み上げ用の本文には全文を残す。

## Open-Meteo取得クライアント

`apps/api/external/openmeteo/fetch`の`NewClient()`でクライアントを作り、`FetchForecast(ctx)`で外部API用の`model.Forecast`を取得する。`apps/api/external/openmeteo`の`NewForecastReader(fetcher, now)`が取得結果をmapperへ渡し、検証済みの予報をキャッシュへ返す。取得日時には通信完了後の`now()`を使用する。

- 取得先：`https://api.open-meteo.com/v1/forecast`。認証不要。
- 固定パラメーター：東京都庁の緯度・経度、`timezone=Asia/Tokyo`、`forecast_days=5`、`temperature_unit=celsius`。
- 日別項目：`weather_code`、`temperature_2m_max`、`temperature_2m_min`、`relative_humidity_2m_mean`。
- HTTPクライアントのタイムアウトは10秒。呼び出し元のContextによるキャンセルも受け付ける。
- 通信失敗・200以外のHTTPステータス・JSONの解析失敗はエラーとして返す。レスポンス本文は利用後にCloseする。
- 外部レスポンスの並列配列とnullをそのまま保持する。天気コード変換・日付や配列の整合性検証は後述の変換処理で行う。
- `Forecast.Daily`は値型とする。`daily`自体の欠損と空オブジェクトは区別せず、後続の配列の整合性検証で不足を検出する。配列内の気温・湿度・天気コードはnullと0を区別するためポインターを使う。
- テストは外部APIへ接続せず、HTTP Transportを差し替えて正常系（リクエスト内容・数値・欠損値）、HTTPエラー、JSON解析エラーの3ケースに絞り、各ケースでCloseも確認する。

## 予報の変換・検証

予報日数は`domain/model.WeatherForecastDays`（5日）に統一し、取得リクエストと配列の検証で共有する。日数の変更時はOpenAPIの`minItems`・`maxItems`と関連資料も同時に更新する。

`apps/api/external/openmeteo/mapper`の`ToWeatherForecast(forecast, fetchedAt)`で、外部レスポンスを`domain/model.WeatherForecast`へ変換する。Domainは外部APIやOpenAPIの型に依存しない。HTTPレスポンス用の生成モデルへの変換は`handler.WeatherHandler`で行う。

- 取得日時を日本時間（UTC+9）へ変換し、その暦日を「今日」とする。タイムゾーンDBのないコンテナでも動作するよう固定オフセットを使う。
- 日付・天気コード・最高／最低気温・平均湿度の配列が、それぞれ5件あることを確認する。
- 日付を日本時間で解釈し、今日から連続する5日間が昇順で並んでいることを確認する。並べ替えや不足分の補完はしない。
- 気温と湿度のnullは保持する。湿度の値がある場合は0〜100%の範囲を検証する。気温には独自の上下限を設けない。
- 天気コードを上記のenumへ変換する。未対応のコードと欠損は`unknown`にする。
- 検証に失敗した場合はエラーを返し、変換途中の結果は返さない。

テストは日本時間の日付境界、数値・欠損値の保持、各配列の件数、日付の不正・重複・順序、湿度の境界、全対応コードの変換を確認する。
