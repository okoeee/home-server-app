# 今日の値動き注目株 設計

## 目的

東証普通株を対象に、取引終了後の日足から、普段より値動きと売買が活発だった10銘柄を抽出する。

本機能は当日の市場を振り返るためのものであり、将来の株価予測や売買推奨を目的としない。

## バージョン1の範囲

- 日足だけを使う。
- 上昇と下落の両方を対象にする。
- ニュース、決算、適時開示、OpenAI APIは使わない。
- 算出条件は初期仮説としてバージョン管理する。

## データの流れ

```text
J-Quants API
    ↓
銘柄マスターと日足をMySQLへ保存
    ↓
分析対象を絞り込む
    ↓
指標と注目度を計算
    ↓
上位10銘柄と算出根拠を保存
    ↓
Go APIから返す
```

## データ取得元

[J-Quants API](https://jpx-jquants.com/) v2を使用する。

### 銘柄マスター

分析対象の判定と画面表示に、次の情報を使用する。

| 項目 | 用途 |
| --- | --- |
| 証券コード | 銘柄の識別 |
| 会社名 | 画面表示 |
| 市場区分 | Prime、Standard、Growthの表示 |
| 商品区分 | 普通株とETF・REITなどの区別 |
| 33業種 | 業種の表示 |
| 適用日 | 対象日時点の銘柄情報の判定 |

### 株価日足

| 項目 | 用途 |
| --- | --- |
| 取引日 | 対象日の特定 |
| 証券コード | 銘柄マスターとの紐付け |
| 調整済み始値 | 日足の保存 |
| 調整済み高値 | 値幅と高値更新の計算 |
| 調整済み安値 | 値幅と安値更新の計算 |
| 調整済み終値 | 騰落率の計算 |
| 調整済み出来高 | 出来高倍率の計算 |
| 売買代金 | 流動性の判定 |
| 調整係数 | 株式分割などの確認 |
| 取得日時 | 取得処理の確認 |

価格推移の比較には調整済みの値を使う。流動性の判定には売買代金を使う。

### 数値の精度

J-Quantsの日足APIでは、調整済み価格と調整済み出来高が小数第1位まで配信される。

`daily_prices`では、調整済み価格を`DECIMAL(14, 1)`、調整済み出来高を`DECIMAL(20, 1) UNSIGNED`で保存する。出来高は価格より大きな値になるため、価格より整数部を広く確保する。

Goでは2進浮動小数点による誤差を避けるため、`github.com/shopspring/decimal`の`decimal.Decimal`を使用する。

### 調整済みとは

株式分割や株式併合があると、企業価値の変化とは関係なく、1株あたりの価格と出来高が大きく変わる。

例えば、1株を2株に分割すると、理論上は次のように変化する。

```text
分割前: 株価2,000円、出来高100株
分割後: 株価1,000円、出来高200株
```

調整前の値だけを比較すると、株価が50%下落し、出来高が2倍になったように見える。しかし、これは通常の売買による変化ではない。

調整済み価格は、株式分割や株式併合の影響を補正し、異なる取引日の価格を同じ基準で比較できるようにした値である。調整済み出来高も、価格と対応するように過去の出来高を補正した値である。

本機能では、見かけ上の急騰・急落や出来高急増を検出しないよう、騰落率、高値・安値、値幅、出来高倍率の計算に調整済みの値を使う。

J-Quantsの調整済み値は、後日の株式分割などを受けて過去分が再計算される場合がある。そのため、過去データの再取得方法はデータ取得処理を設計するときに決める。

## 取得期間

算出には、対象日と過去20営業日の日足が必要になる。

```text
初回取得: 過去60営業日程度
日次取得: 当日の1営業日分
```

60営業日は、欠損への対応と将来の指標追加に備えた初期値とする。

### 初回取得と日次取得

初回取得と日次取得で別々の取得処理は作らず、同じプログラムへ対象期間を渡して実行する。

```text
初回取得: 開始日から終了日までを指定する。
日次取得: 1営業日を指定する。
```

実行イメージは次のとおりとする。

```bash
import-prices --from 2026-07-01 --to 2026-10-14
import-prices --date 2026-10-14
```

取得プログラムは`apps/api/cmd/import-prices`への配置を想定する。

バージョン1の初回取得は過去60営業日程度とする。52週高値や6カ月・12カ月モメンタムを追加するときに、必要な過去期間を延ばす。

期間取得は日付単位で進捗を記録し、途中で失敗しても完了済みの日付を含めて安全に再実行できるようにする。

## 更新タイミング

J-Quantsの公式情報では、株価四本値は日次で16:30 JST、上場銘柄情報は日次で17:30 JSTに更新される。

- [株価四本値](https://pro.jpx-jquants.com/datasets/9)
- [上場銘柄情報](https://pro.jpx-jquants.com/datasets/4)

契約プランによって提供の遅延が異なるため、当日データを取得できるプランを前提とする。

自宅サーバーでは営業日の18:00 JST以降に次の順序で実行する。

```text
1. 銘柄マスターを取得する。
2. 当日の日足を取得する。
3. 取得した日付と件数を確認する。
4. 注目度を計算する。
5. 上位10銘柄を保存して公開する。
```

非営業日は処理しない。取得した最新日が期待する取引日と一致しない場合も、その日のランキングを作成しない。

## 上場廃止銘柄

上場廃止になった銘柄も、過去の日足とランキング結果は削除しない。削除すると過去日のランキングを再現できなくなるためである。

```text
上場中: 日次取得とランキングの対象にする。
上場廃止: 新しい日足の取得対象から外し、過去データは保存する。
```

銘柄マスターには、J-Quantsから取得した現在の銘柄情報と上場状態を持たせる。

```text
stocks
├── symbol
├── effective_date
├── company_name
├── sector_33_code
├── sector_33_name
├── market_code
├── market_name
├── product_category_code
├── is_listed
├── created_at
└── updated_at
```

J-Quantsの上場銘柄マスターは、上場日と上場廃止日を提供しない。正確な値を取得できないため、バージョン1では`listed_from`と`delisted_on`を持たず、`is_listed`で現在の取得対象かどうかを管理する。

将来、JPXなどから正確な上場廃止日を取得する場合は、上場廃止情報を別テーブルとして追加する。

銘柄一覧に存在しなかったことだけを理由に、すぐ上場廃止へ更新しない。ページネーションを含む全件取得が正常終了し、取得件数にも異常がないことを確認してから状態を更新する。

会社名や市場区分の変更履歴が必要になった場合は、銘柄マスターの履歴テーブルを追加する。バージョン1では現在状態だけを管理する。

## 同じ日足を取得した場合

日足は証券コードと取引日の組み合わせで一意にする。

```sql
PRIMARY KEY (symbol, trade_date)
```

同じ証券コードと取引日のデータを再取得した場合は、エラーや無視ではなくUPSERTによって既存値を更新する。

```text
未登録: 新しく登録する。
登録済みで同じ内容: 実質的な変更は発生しない。
登録済みで異なる内容: APIから再取得した値で更新する。
```

J-Quantsの調整済み値は、後日の株式分割などによって過去分が再計算される可能性があるため、重複データを常に無視する方法は採用しない。

対象日の日足は、可能な範囲で同じトランザクション内に保存する。途中で保存に失敗した場合はロールバックし、一部の銘柄だけが保存された状態を避ける。件数が大きくなった場合は一定件数ごとの処理に分割する。

## データ取得履歴

初回取得と日次取得の成否を確認できるよう、取得処理の実行履歴を保存する。

```text
ingestion_runs
├── id
├── data_type
├── target_from
├── target_to
├── started_at
├── completed_at
├── fetched_count
├── saved_count
├── status
└── error_message
```

同じ期間の取得処理は再実行できるようにする。日足のUPSERTと取得履歴によって、途中失敗からの再開と結果確認を可能にする。

## 分析対象

次の条件をすべて満たす銘柄を対象にする。

- 東証上場の普通株である。
- 対象日時点で上場中である。
- 当日の日足と出来高が存在する。
- 前営業日の終値が存在する。
- 過去20営業日分の日足が存在する。
- 過去20営業日の平均売買代金が1億円以上である。

平均売買代金1億円は、低流動性銘柄を除くための暫定値であり、検証後に変更できるようにする。

## 算出ロジック

過去の平均や最高値を計算するときは、計算対象の当日を含めない。

### 絶対騰落率

```text
当日の騰落率 = 当日の調整済み終値 ÷ 前営業日の調整済み終値 - 1
絶対騰落率 = 当日の騰落率の絶対値
```

上昇、下落、変化なしの方向も保存する。

### 出来高倍率

```text
出来高倍率 = 当日の調整済み出来高 / 対象日より前の直近20件の調整済み出来高平均
```

現在の実装では、銘柄ごとの保存済み日足を新しい順に20件使用する。取引停止や欠損がある場合、20営業日より長い期間になることがある。履歴が20件に満たない銘柄、平均出来高がゼロの銘柄は計算対象から外す。

### 日中値幅率

```text
日中値幅率 = (当日の調整済み高値 - 当日の調整済み安値) / 前営業日の調整済み終値
```

### 20日高値・安値更新

```text
過去20営業日の最高値 = 前営業日までの20営業日における調整済み高値の最大値
過去20営業日の最安値 = 前営業日までの20営業日における調整済み安値の最小値
```

```text
上方更新: 当日の調整済み終値が過去20営業日の最高値を上回る
下方更新: 当日の調整済み終値が過去20営業日の最安値を下回る
更新なし: いずれにも該当しない
```

## スコアリング

絶対騰落率、出来高倍率、日中値幅率を、当日の分析対象銘柄内で0から100のパーセンタイルスコアへ変換する。

```text
値動きスコア
出来高スコア
値幅スコア
```

20日高値または安値を更新した場合は高安値更新スコアを100、更新していない場合は0とする。

バージョン1の注目度は次の式で計算する。

```text
注目度 =
    値動きスコア × 0.35
  + 出来高スコア × 0.30
  + 値幅スコア   × 0.20
  + 高安値更新スコア × 0.15
```

この式と重みは、既存文献をそのまま再現したものではなく初期仮説である。`algorithm_version`として`v1`を保存する。

## 順位

次の優先順位で並べ、先頭10件を採用する。

```text
1. attention_scoreの降順
2. volume_ratioの降順
3. 20日平均売買代金の降順
4. 証券コードの昇順
```

同じ入力とアルゴリズムから、常に同じ結果になるようにする。

## 公開条件

日足の取得、対象日の確認、スコア計算、結果保存がすべて成功した後に、その日のランキングを公開する。

途中で失敗した場合は、前営業日の結果を当日分として表示せず、本日分が未生成であることを返す。

## 既存テーブル

現在の`daily_prices`は、1銘柄・1取引日につき1件の日足を保存する。

テーブル定義は`apps/database/mysql/init/table_schema.sql`、動作確認用の1件は`apps/database/mysql/init/table_seed.sql`で管理している。サンプル値は実際の株価ではない。

今後、売買代金、調整係数、取得日時を追加する必要がある。また、銘柄マスター、取得履歴、スクリーニング結果の各テーブルを追加する。

## スキーマ変更

初期化SQLは、空のDockerボリュームからMySQLを作るときだけ実行される。既にデータが入ったDBへ`table_schema.sql`の変更は自動適用されない。

開発初期で保存データを破棄できる間は、初期化SQLを修正してDBを作り直す方法も使える。ただし、ボリューム削除は保存データを失うため、実行前に対象を確認する。

実データを保存し始めた後は、次のような連番付きマイグレーションで変更する。

```text
apps/database/mysql/migrations/
├── 000001_create_daily_prices.sql
├── 000002_add_turnover_value.sql
└── 000003_create_screening_tables.sql
```

例えば、売買代金を追加する変更は次のような`ALTER TABLE`として管理する。

```sql
ALTER TABLE daily_prices
    ADD COLUMN turnover_value DECIMAL(20, 2) NULL COMMENT '売買代金';
```

安全な移行は次の順序で行う。

```text
1. NULLを許可した新しいカラムを追加する。
2. 既存データを埋める。
3. APIを新しいカラムへ対応させる。
4. 必要なら最後にNOT NULL制約を追加する。
```

適用済みのマイグレーションは再実行せず、どこまで適用済みかをDBで管理する。実データを蓄積する前に、Gooseやgolang-migrateなどのマイグレーションツールを選定する。

スキーマまたはクエリを変更した後は、sqlcのコードも再生成する。

```bash
make generate-sqlc
```

生成コード、スキーマ変更、クエリ変更は同じコミットに含める。
